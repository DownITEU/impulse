# Wand source

- `app` registers `Wand` through the capability traits in `model`. Keep source-specific behavior in this crate.
- Never bundle or commit third-party binaries. Check hashes and publisher signatures before loading them (`PUBLISHERS`: WeMod LLC, and its earlier name Daring Development Inc. on older trainers); keep verified images locked until the run ends. The service and plugin are those of the trainer's architecture (`binaries`), as Wand picks them.
- Keep credentials inside the session code and protect them with user-scoped DPAPI. Never log tokens, auth codes, headers or response bodies.
- Treat remote ids, paths and links (`purchaseUris`, reaching `launchers::store_link` only) as untrusted. Preserve listener scope and limits. Read the user's installation and settings without modifying them.
- `launch.proxy` (`proxy.rs`) is the one write into a game's folder, for a store's start only: Wand's `GameLauncher.exe` from its install, signature-checked, stands in for the launcher, which waits beside it as `.wand-backup`, with `.wand-config` naming what to start. Its paths are plain relative files, and the folder written is the game's after links resolve. A leftover it cannot account for is refused, never overwritten; the stand-in's own `.wand` and `.wand-config` are replaced. The stand-in puts the launcher back itself once the game starts; dropping the mount does too, off the dropping thread, and a retry's mount waits for that restore. The stand-in runs on its own and is not held locked: it moves itself aside.
- The process looked for is `target.image`, else the proxy's `gameExe`: never the anti-cheat's launcher. `blueprint.notes` reach the UI as the trainer's notes, in the answer's language.
- The game version a run sends is the install's build (`attach`'s, the catalog `versionPath`'s stamp the scan read), 0 when unknown: Wand's `gameVersion ?? 0`, never the running exe's. Before the service goes in, a last session's teardown in that process is waited for as Wand does (`Local\TophatService_TeardownComplete_<pid>`, 30 s; late only warns).
- `activate.flags` (suspended start, hidden threads, masked modules, an external host) are not done: an unmarked attach failure of such a trainer says so and logs them. A service that never dials in asks for a newer Wand.
- The overlay (`overlay/`, `Overlays`): Wand's `overlay_game_x64.dll` / `overlay_game.dll` from the install, by the game process's architecture (`agent::x64`), signature-checked, `agent::map`ped once per process under one lock (a second `enter` only waits for the link; a failed load is not tried again: a timed-out one may still land) and kept locked until that process is gone; only for a game whose catalog `flags` has 256. The DLL dials a hidden window titled with its own fixed name: one host thread per app, `Refused` while Wand's own host holds it. Every CONNECT is answered at once (ACK, or the goodbye while resting): one left unanswered stays connecting for good, even to a later host, and a DLL from an earlier session dials before `enter` records its game. Frames go only to a canvas of a process we mapped. A game's link lasts while that game runs: the DLL tears down and rebuilds its graphics on every disconnect (a game froze on it), so a closed canvas only closes its layers. With no canvas and no link of a game we mapped, the host rests (it starts so: a failed `enter` must not hold Wand's title): its window is renamed first, then the other links get tinyipc's goodbye, so a DLL retries every second until a canvas wakes the host (a goodbye said while findable makes it dial again at once). A host that exits while linked is redialled by the DLL. Every message to it is sent from the host thread (never inside the DLL's own send) and built with serde: a malformed one kills the DLL's thread. An interactive layer is a window with `accept_input` and `block_input` (the DLL sends its input, the game gets none of it; keys only once the window is clicked); `block` is the DLL's global block, told only while an interactive layer is up (never input lost to nothing shown) and lifted when its canvas closes; a closed canvas's last words go again while sends are late. The DLL's own hotkey is key 0: ours asks for the block. A layer's cursor goes on change, by its `IDC_*` name (a window described anew has the arrow). A canvas hears the DLL only once `Ready`, which brings the size it last reported. Frames are re-sent 250 ms after `graphics-window-info` (the DLL drops them); after a timed-out send the whole state goes again. A texture on another adapter ends the canvas. The decisions are `state.rs` (no Win32 but the window memory), the sending is `host.rs`.
- Never prefetch trainers. A trainer DLL the CDN cannot give (a 404 that depends on the user's network, an offline start) is taken from Wand's own download (`%APPDATA%\<brand>\App\trainers\Trainer_<id>_<hash10>.dll`, read only), only when it hashes to the one the API names, and copied into ours.
- API errors log method, path and HTTP status when available, never the query or response body. A `TypeError` triggers a credential-free `no-cors` probe of the origin; its result is not a CORS diagnosis.
